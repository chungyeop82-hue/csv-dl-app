# 아키텍처 설계 (ARCHITECTURE)

- 대상: 학생용 Windows 11 PC에서 단독 실행하는 CSV 딥러닝 웹앱
- 작성일: 2026-09-19 / 최종 수정: 2026-09-28 / 상태: 구현 진행 중 (STEP 4~6 코드 구현 완료, 실행 검증은 진행 중, 잡 상태 정의는 SPEC.md v0.4와 동기화)
- 짝 문서: [ENV_CHECK.md](./ENV_CHECK.md) (이 PC가 어떤 실행 모드에 해당하는지 판정), [SPEC.md](./SPEC.md) (잡 상태·제출 형식 등 기능 요구사항의 기준 문서)

## 1. 목적과 범위

**목적.** 사용자가 CSV를 올리면 브라우저에서 전처리 → 딥러닝 학습 → 평가 → 결과 내려받기까지 한 PC 안에서 끝낼 수 있는 웹앱.

**포함(MVP).**
- CSV 업로드와 자동 프로파일링(컬럼 타입, 결측, 분포 요약)
- 표 형태(tabular) 데이터용 소형 신경망(MLP)의 분류·회귀 학습
- 학습 진행률·지표 확인, 결과(예측 CSV, 모델 파일, 리포트) 내보내기
- 한 번에 학습 작업 1개만 허용하며, queued 또는 running 상태의 활성 작업이 있으면 새 학습 요청은 즉시 거절한다.

**제외(비목표).** 다중 사용자·로그인, 인터넷 공개 배포, 분산·다중 GPU 학습, 수 GB급 대용량 데이터, 이미지·텍스트 모델.

## 2. 설계 원칙과 제약

| 구분 | 내용 |
|------|------|
| 제약 | 8GB RAM, 여유 디스크 15GB, GPU는 있을 수도 없을 수도 있음, 관리자 권한·가상화도 보장되지 않음 |
| 원칙 1 | **단독 실행**: 외부 서버·DB·인증·메시지 큐 없이 PC 한 대에서 동작. 실행 단계는 오프라인 가능 |
| 원칙 2 | **가장 단순한 구성**: 컨테이너 1개, 프로세스 역할 2개(웹 + 학습 워커 1개), 저장소는 SQLite + 파일 |
| 원칙 3 | **Docker는 배포 수단일 뿐**: 앱 코드는 Docker 전용 가정을 하지 않음. 경로·장치·포트는 환경 변수로 주입해 네이티브 실행(폴백)도 같은 코드로 동작 |
| 원칙 4 | **8GB 우선**: 동시 학습 금지, 데이터·모델 크기 상한, 무거운 라이브러리는 워커에서만 로드 |
| 원칙 5 | **결과는 눈에 보이는 폴더로**: 내부 상태는 볼륨, 사용자가 가져갈 결과물은 `./exports` |

## 3. 전체 구조

```text
Windows 11 호스트
├─ 브라우저 ── http://127.0.0.1:8080 ─────────────┐
├─ 프로젝트 폴더/exports  (바인드 마운트) ◀──────────┼──────────┐
│                                                  ▼          │
└─ Docker Desktop (WSL 2 백엔드)                                │
   ┌────────────────── app 컨테이너 (단일) ─────────────────┐    │
   │                                                        │    │
   │  [웹 프로세스]  단일 워커 uvicorn + 웹 프레임워크         │    │
   │    ├ REST API + 정적 UI                                 │    │
   │    ├ 잡 디스패처 (활성 잡 1건 → 워커 실행)                │    │
   │    └ SQLite 읽기/쓰기                                   │    │
   │            │ submit                                     │    │
   │            ▼                                            │    │
   │  [학습 워커]  ProcessPoolExecutor(max_workers=1)         │    │
   │    └ 전처리 → 학습 → 평가 → 결과 저장 (torch는 여기서만)   │    │
   │                                                        │    │
   └────────────┬───────────────────────────────┬───────────┘    │
        /data    │ (명명된 볼륨 appdata)          │ /exports ──────┘
   db · uploads · models · logs · tmp              결과물(예측, 모델, 리포트)
```

- **한 컨테이너, 두 역할.** 웹 프로세스가 시작될 때 워커 풀(프로세스 1개)을 만들고, 학습은 항상 그 자식 프로세스에서 실행합니다. 별도 워커 컨테이너나 큐 서버는 두지 않습니다.
- **웹 프레임워크는 열린 결정입니다.** 기본 제안은 Python + FastAPI(uvicorn)이며 [10절](#10-열린-결정-사항)에서 착수 시 확정합니다. 어느 쪽을 택하든 아래 구조(단일 웹 프로세스, 워커 1개)는 유지됩니다.
- **진행 상황 전달(구현 완료, STEP 6).** 학습 워커(자식 프로세스) → 웹 프로세스(디스패처)는 **멀티프로세싱 Queue**로, 웹 프로세스 → 브라우저는 **SSE**(디스패처가 SQLite를 1초 주기로 폴링해 바뀐 내용만 전송)로 전달합니다. 두 구간 모두 SQLite `jobs`/`job_events`를 매개로 합니다. 자세한 흐름은 [5-2절](#5-2-잡-흐름)을 참고하세요.

## 4. 컨테이너와 저장소

### 4-1. app 단일 컨테이너

| 항목 | 내용 |
|------|------|
| 이미지 | 하나의 Dockerfile에서 **CPU 타깃**과 **GPU 타깃** 두 가지를 빌드 (디스크·다운로드 절약을 위해 기본은 CPU). 빌드 타깃은 `cpu-runtime`/`gpu-runtime`. GPU는 `compose.gpu.yaml`을 겹쳐 선택하며 같은 `app` 서비스를 대체함(동시 실행 없음, 컨테이너는 항상 1개) |
| 포트 | 개발용 compose.yaml: 호스트 **127.0.0.1:8080** → 컨테이너 8000 으로만 게시(외부 네트워크에 열지 않음). 학생 배포판 `dist/compose.dist.yaml`은 같은 Wi-Fi(LAN) 접속을 위해 `0.0.0.0:8080`으로 게시한다(STEP 10, 인터넷 공개는 아님 - 자세한 내용은 DEPLOY.md 8절) |
| 사용자 | 비루트 사용자로 실행 |
| 리소스 | 컨테이너 메모리 한도 설정(WSL 상한 4GB 기준으로 약 3GB 안팎에서 시작, 튜닝), 재시작 정책은 안전한 재시작 위주 |
| 헬스체크 | `/health` 엔드포인트 (웹 프로세스 + DB 접근 + 워커 풀 상태) |
| 실행 | `docker compose` 한 명령. 더블클릭용 시작/종료 스크립트는 구현 단계에서 제공 |

### 4-2. `appdata` 명명된 볼륨 (내부 상태)

컨테이너의 `/data`에 마운트하는 Docker 관리 볼륨이며, 앱의 **모든 내부 상태**를 여기에 둡니다.

| 경로 | 내용 |
|------|------|
| `/data/db/app.db` | SQLite 데이터베이스 |
| `/data/uploads/` | 업로드한 원본 CSV (`<uuid>.csv`로 보관, 원본 파일명은 SQLite에 기록) |
| `/data/models/` | 학습 체크포인트와 최종 모델 |
| `/data/logs/` | 앱·잡 로그 (크기 순환) |
| `/data/tmp/` | 임시 파일 (시작 시 정리) |

**왜 바인드 마운트가 아니라 명명된 볼륨인가.**
- SQLite의 WAL 모드는 공유 메모리와 파일 잠금을 사용하는데, Windows 폴더를 컨테이너에 바인드 마운트하면 네트워크형 파일 시스템을 거쳐 **잠금·성능 문제와 DB 손상 위험**이 생길 수 있습니다.
- 볼륨은 WSL 2 내부의 리눅스 파일 시스템(ext4)에 저장되어 빠르고 안전합니다.
- 대신 사용자가 탐색기로 직접 열어 보기 어렵다는 단점이 있으므로, 사용자에게 필요한 결과물은 별도로 `./exports`에 내보냅니다.

**수명 주기.** 컨테이너를 지우거나 이미지를 다시 빌드해도 볼륨은 유지됩니다. 완전 초기화는 "볼륨 삭제"라는 명시적 조작이며, 삭제 전 백업 방법(내보내기)을 안내합니다.

### 4-3. `./exports` 바인드 마운트 (결과물)

프로젝트 폴더의 `exports/`를 컨테이너의 `/exports`에 바인드 마운트합니다. 사용자가 탐색기·엑셀·다른 도구로 바로 가져다 쓰는 **유일한 공개 출력 경로**입니다.

- **쓰기 방식**: 임시 이름으로 완성한 뒤 이름을 바꾸는 방식(원자적 쓰기)으로 저장해, 반쯤 쓴 파일이 노출되지 않게 합니다.
- **폴더 구성**: 실행 1건당 `exports/<날짜시각>_<데이터셋>_<run번호>/` 하나. 안에는 예측 CSV, 모델 파일, 지표·설정 요약 리포트를 둡니다.
- **파일명 규칙**: Windows 금지 문자 제거, 길이 제한, 한글은 허용하되 충돌 시 번호 부여.
- **CSV 인코딩**: 엑셀에서 바로 열리도록 UTF-8 BOM 옵션 제공(기본값은 UI에서 선택).
- **권한**: 컨테이너 비루트 사용자가 쓸 수 있도록 구현 단계에서 확인 항목에 포함.
- **경로 권장**: 프로젝트를 한글·공백 없는 경로(예: `C:\work\csv-dl-app`)에 둡니다. 이 PC는 사용자 폴더명이 한글이므로 그 아래는 피합니다.

### 4-4. SQLite (메타데이터 저장소)

- **역할**: 데이터셋·잡·내보내기 이력의 메타데이터. 대용량 본문(CSV, 모델)은 파일로 두고 DB에는 경로와 해시만 저장.
- **설정 방침**: WAL 모드, 외래 키 사용, 바쁨 대기(busy timeout) 설정, 잡 상태 변경은 짧은 트랜잭션으로.
- **접근 규칙**: 웹 프로세스와 워커 프로세스가 **각자 자기 연결**을 엽니다. 연결 객체를 프로세스 간에 공유하지 않습니다. 단, 잡 진행 중 SQLite에 쓰는 주체는 **항상 웹 프로세스(디스패처)** 하나뿐입니다 — 워커(자식 프로세스)는 DB에 직접 접근하지 않고 멀티프로세싱 Queue로만 진행 상황을 넘깁니다(5-2·5-3절).
- **스키마 개요** (구현 완료, STEP 6):

| 테이블 | 주요 내용 |
|--------|-----------|
| `datasets` | 원본 파일명, 저장 파일명(`<uuid>.csv`), 원본 해시, 파일 크기, 인코딩, 전체·사용 행 수, 열 수, 샘플링 여부, 프로파일 요약(JSON: 열 타입·결측·고유값·미리보기), 생성 시각 |
| `jobs` | **잡(Job)과 실행(Run)을 하나로 관리**: 데이터셋 ID, 작업 종류(분류/회귀)·타깃 열·설정(JSON), 상태(5-2절: queued/running/completed/failed/cancelled/timeout/interrupted), 사용 장치(cpu/cuda), 진행률(JSON, 최신 에포크 스냅샷), 지표(JSON, 검증·테스트·베이스라인), 모델·전처리 객체 경로, 오류 코드, 취소 요청 플래그, 생성·시작·종료 시각 |
| `job_events` | 잡 ID, 시각, 수준, 메시지, 진행률 페이로드(JSON) — 에포크별 로그이자 SSE·폴링 화면 표시용 이력 |
| `exports` | 잡 ID, 내보낸 폴더 경로, 종류, 생성 시각 |

**별도 `runs` 테이블을 두지 않은 이유.** 이 앱에서는 잡 1건이 곧 실행(run) 1건이며 재사용되지 않으므로(재시도는 새 잡을 새로 만듭니다), 장치·지표·모델 경로 같은 "실행 결과"를 별도 테이블로 분리할 실익이 없습니다. `jobs` 테이블 컬럼에 그대로 합쳐 조인 없이 한 번에 조회합니다.

- **마이그레이션**: 스키마 버전 번호(`PRAGMA user_version`)를 DB에 저장하고 시작 시 확인해 이전 버전이면 순차적으로 스키마를 적용합니다(현재 버전 2: v1 `datasets`, v2 `jobs`/`job_events` 추가).
- **백업**: 사용자 조작으로 DB와 업로드를 묶어 `exports/backup_*` 로 내보내는 기능을 후순위로 둡니다.

## 5. 학습 워커: ProcessPoolExecutor(max_workers=1)

### 5-1. 왜 워커 1개인가

- 8GB RAM에서는 동시 학습 2건이 곧 OOM입니다.
- GPU가 있어도 VRAM 경합과 속도 저하가 생기므로 직렬 실행이 더 예측 가능합니다.
- 잡을 한 번에 하나만 실행하므로 결과 재현성(시드)과 진행률 표시가 단순해집니다.
- 학습을 **별도 프로세스**로 분리하는 이유: 학습이 파이썬 GIL을 오래 잡아 웹 응답이 멈추는 것을 막고, 학습 프로세스가 죽어도 웹은 살아남게 하기 위함입니다.

### 5-2. 잡 흐름

```text
[브라우저] ─ 학습 요청(POST /jobs) ─▶ [웹] 데이터셋·타깃 검증 후 잡을 DB에 queued로 기록
                                        (이미 queued/running 잡이 있으면 즉시 거절: E-JB-001)
[디스패처] 0.3초마다 확인. 실행 중 잡이 없으면 가장 오래된 queued를 꺼내 running으로 표시,
           멀티프로세싱 Queue와 취소 플래그(공유 Value)를 새로 만들어 ProcessPoolExecutor(spawn,
           max_workers=1)에 submit
[워커, 자식 프로세스] 전처리 → 학습 → 평가 → 베이스라인 비교 → 모델·전처리 객체 저장
    └ 에포크가 끝날 때마다 진행 상황을 콜백 → 멀티프로세싱 Queue에 담아 디스패처로 전달
    └ 에포크 경계마다 공유 취소 플래그를 확인해, 켜져 있으면(취소 또는 시간초과) 학습을 멈춤
[디스패처] 매 틱마다 Queue를 비워 SQLite jobs.progress_json과 job_events에 기록
           (SQLite에 쓰는 주체는 항상 디스패처 하나뿐, 워커는 DB에 직접 접근하지 않음)
[디스패처] 경과 시간이 최대 학습 시간(기본 10분, APP_MAX_TRAIN_SECONDS로 조정)을 넘거나
           API로 취소 요청(cancel_requested)이 들어오면 공유 취소 플래그를 켬
[디스패처] 워커 종료 시 결과에 따라 completed / failed / cancelled / timeout 을 SQLite에 기록
           ─▶ 다음 queued 처리
[브라우저] GET /jobs/{id}/events 로 SSE 연결, 또는 GET /jobs/{id} 로 폴링
[웹] SSE는 SQLite를 1초 주기로 확인해 이전과 달라진 내용만 전송, 잡이 종료 상태가 되면 스트림도 종료
```

**잡 상태 (SPEC.md 5-4절과 동일, 고정).** `queued → running → completed | failed | cancelled | timeout | interrupted`

| 상태 | 의미 | 화면 표시 |
|------|------|-----------|
| `queued` | 대기중: 아직 워커에 배정되지 않음 | 대기중 |
| `running` | 실행중: 워커가 학습 중 | 실행중 |
| `completed` | 완료: 정상 종료 (예전 명칭 `succeeded`는 더 이상 쓰지 않고 **completed로 통일**) | 완료 |
| `failed` | 실패: 오류로 중단 | 실패 |
| `cancelled` | 취소: 사용자가 취소 요청 | 취소 |
| `timeout` | 시간초과: 최대 학습 시간(기본 **10분**) 초과로 자동 중단 | 시간초과 |
| `interrupted` | 중단됨: 앱 재시작 시 `running`이었던 잡을 복구한 상태 | 중단됨 |

- **timeout 처리 규칙.** 디스패처는 잡을 워커에 넘길 때 시작 시각을 기록하고, 매 틱(0.3초)마다 경과 시간을 확인한다. 경과 시간이 최대 학습 시간(기본 10분, 환경 변수 `APP_MAX_TRAIN_SECONDS`로 조정 가능)을 넘으면 공유 취소 플래그를 켜서 워커가 다음 에포크 경계에서 학습을 멈추게 하고, 워커가 멈춘 뒤 디스패처가 잡 상태를 DB에 `timeout`으로 저장한다(취소 요청 때문에 멈췄는지 시간초과 때문에 멈췄는지는 디스패처만 구분해 최종 상태에 반영한다). 화면에는 오류가 아니라 **정보 상태**로 "학습이 제한 시간(10분)을 초과하여 자동 중단되었습니다"와 같은 한국어 안내를 표시한다(SPEC.md 8-3절과 동일한 원칙: `취소`·`시간초과`·`중단됨`은 오류 화면이 아니라 정보 상태로 표시).
- **재시작 복구 규칙.** 앱(웹 프로세스)이 재시작될 때, 디스패처를 시작하기 전에 DB에 `running`으로 남아 있는 잡을 모두 `interrupted`(중단됨)로 갱신한다. 이 역시 오류가 아니라 정보 상태로 화면에 표시한다. 이번 학기 범위에서는 **상태 표시까지만** 구현하며, 마지막 체크포인트에서 이어 학습(SPEC.md FR-32)하는 기능은 아직 없다 — 아래 5-3절의 체크포인트 항목 참고.

### 5-3. 반드시 지킬 구현 규칙

| 규칙 | 이유 |
|------|------|
| 풀 생성 시 시작 방식을 **spawn으로 명시** | CUDA는 fork된 자식 프로세스에서 다시 초기화할 수 없고, 파이썬 버전에 따라 기본 시작 방식이 달라짐 |
| 웹 프로세스에서 **torch를 가져오지 않음** | 웹 프로세스 메모리(수백 MB)를 아끼고, GPU 컨텍스트를 워커에만 생성 |
| 워커 함수에는 **잡 ID와 설정만 전달**, 큰 데이터는 파일 경로로 전달 | 프로세스 간 직렬화 비용과 메모리 이중 사용 방지 |
| **진행률은 멀티프로세싱 Queue로 워커→디스패처에 전달**, SQLite 기록은 **디스패처(웹 프로세스)만** 수행 | 자식 프로세스가 DB 연결을 직접 열 필요가 없고, 웹 프로세스가 쓰기를 도맡아 연결 경쟁을 피함. 화면은 SQLite를 SSE·폴링으로 보기만 하면 됨 |
| **취소는 협조적 방식**: API가 취소 요청을 SQLite(`cancel_requested`)와 디스패처에 함께 남기면, 디스패처가 공유 플래그(멀티프로세싱 `Value`)를 켜고 워커가 에포크 경계마다 그 플래그만 확인해 멈춘다 | 이미 실행 중인 풀 작업은 `Future.cancel()`로 멈출 수 없고, 워커가 DB를 직접 확인할 필요도 없어짐. API 요청이 처리되는 스레드와 디스패처의 이벤트 루프가 다르므로, DB 플래그를 최종 근거로 두고 공유 플래그 갱신은 지연을 줄이는 최적화로만 취급한다 |
| **timeout도 협조적 방식**: 디스패처가 매 틱마다 경과 시간을 확인해 최대 학습 시간을 넘으면 같은 공유 플래그를 켜고, 워커는 에포크 경계에서 그 플래그만 확인해 멈춘다 | 취소와 같은 방식으로 처리해 워커 안에 별도 시계·감시 로직이 필요 없음 |
| 취소가 안 먹거나 무응답이면 **풀을 강제 종료 후 재생성** | 마지막 수단. 해당 잡은 `cancelled`/`failed`로 기록 |
| 워커가 OOM 등으로 죽으면(풀 손상, `BrokenProcessPool`) **잡을 failed 처리하고 풀 재생성** | 풀이 깨진 채로 남으면 이후 모든 잡이 실패함 |
| **모델 저장은 학습이 정상 종료됐을 때 한 번** (최종 가중치 + 전처리 객체) | 이번 학기 범위는 상태 복구(재시작 시 `interrupted` 표시)까지이며, 에포크별 체크포인트 저장과 거기서부터의 이어 학습(SPEC.md FR-32)은 아직 구현하지 않은 후속 항목이다 |
| 실행 시작 시 **장치 자동 선택**(cuda 가능하면 cuda, 아니면 cpu) 후 `jobs.device`에 기록 | GPU 유무에 따라 코드 분기 없이 동작 |
| **torch는 `app/ml/device.py`·`app/ml/tabular.py`, 그리고 워커 함수 안에서만, 함수 안에서 지연 import** | 웹 프로세스가 `app.ml`이나 `app.jobs_worker`를 가져와도 torch가 로드되지 않게 함(테스트로 확인) |
| **CPU 모드는 `torch.set_num_threads(2)`, GPU는 `APP_DEVICE` + `torch.cuda.is_available()`로 선택** | 8GB PC에서 CPU를 독점하지 않고, GPU가 없으면 자동으로 CPU로 내려가게 함 |
| 컨테이너 종료 신호를 받으면 **워커에 정상 종료 요청 후 유예 시간** 부여 | 저장 중 종료로 인한 파일 손상 방지 |

### 5-5. 학습 라이브러리 구성 (`app/ml/`)

디스패처·워커 함수가 호출하는 순수 라이브러리입니다. 웹·DB·잡 큐를 알지 못하고, 진행률은 **콜백**으로만 내보냅니다 — 이 콜백을 호출하는 쪽(워커 함수, `app/jobs_worker.py`)이 콜백 안에서 멀티프로세싱 Queue에 진행 상황을 담아 디스패처(웹 프로세스)로 전달하고, SQLite 기록은 디스패처가 전담합니다(5-3절).

| 모듈 | 역할 | torch |
|------|------|-------|
| `preprocess.py` | 타깃 결측 제외, 70/15/15 분할(분류는 층화), 숫자 중앙값·표준화, 범주 최빈값·원-핫, 전처리 객체 joblib 저장·복원 | 사용 안 함 |
| `device.py` | `APP_DEVICE`와 `torch.cuda.is_available()`로 장치 선택, CPU면 `torch.set_num_threads(2)` | 지연 import |
| `tabular.py` | `TabularML`: 소형 MLP 분류·회귀 학습, 에포크 진행률 콜백, 협조적 취소·timeout, 조기 종료, NaN 발산 감지 | 지연 import |
| `baselines.py` | 로지스틱(회귀는 선형)·랜덤 포레스트 베이스라인 | 사용 안 함 |
| `metrics.py` | 분류·회귀 지표(SPEC 6-5) | 사용 안 함 |

`app/jobs_worker.py`의 워커 함수(`run_training_job`)는 위 라이브러리를 순서대로 호출하는 얇은 접착 계층이며, `torch`는 이 함수 안에서만(모델 저장 직전) 지연 import합니다. `app/jobs_worker.py`의 `Dispatcher`는 asyncio 백그라운드 태스크로 웹 프로세스 이벤트 루프 안에서 동작하며, torch를 전혀 가져오지 않습니다.

## 6. 데이터 흐름과 처리 규칙

```text
업로드 ─▶ 검증(크기·형식·인코딩 감지) ─▶ 저장(/data/uploads) ─▶ 프로파일링
  ─▶ 사용자가 타깃 컬럼·문제 유형(분류/회귀) 선택 ─▶ 학습 잡 생성
  ─▶ 전처리(결측 처리·스케일링·범주형 인코딩·학습/검증 분할) ─▶ 학습 ─▶ 평가
  ─▶ /data/models 저장 ─▶ 사용자가 내보내기 실행 ─▶ /exports/<폴더>
```

- **CSV 인코딩**: 한국어 환경의 엑셀 CSV는 CP949(EUC-KR)인 경우가 많으므로 UTF-8(BOM 포함) → CP949 → EUC-KR 순으로 자동 감지합니다(직접 지정은 후속).
- **누수 방지**: 전처리 통계(평균, 범주 목록 등)는 학습 데이터에서만 계산해 검증 데이터에 적용하고, 내보낸 모델과 함께 저장합니다.
- **재현성**: 시드, 설정(JSON), 데이터 해시, 라이브러리 버전을 `jobs`에 남깁니다.

## 8. 폴백 전략

**공통 설계 규칙 (폴백을 값싸게 만드는 장치).**

1. `APP_DATA_DIR`, `APP_EXPORT_DIR`, `APP_DEVICE`(auto|cpu|cuda)를 **환경 변수**로 받는다(네이티브 폴백용 `APP_HOST`, `APP_PORT`는 후속). 컨테이너에서는 compose가 `APP_DEVICE`를 cpu 또는 cuda로 지정한다. 컨테이너 안에서는 `/data`, `/exports`, 네이티브에서는 사용자 지정 폴더를 준다.
2. 앱 코드에 `/data` 같은 컨테이너 전용 경로를 **하드코딩하지 않는다.**
3. 공통 의존성은 `requirements.txt` 한 벌로 두고, **PyTorch 3종만 CPU/GPU 빌드를 분리**한다 (같은 앱 코드, Dockerfile ARG로 버전·인덱스 고정).
4. 시작 시 환경(장치, 메모리, 디스크)을 감지해 `/env`와 화면 상단에 실행 모드를 표시한다.

### 8-1. 실행 모드 정의

| 모드 | 조건 | 실행 방식 | 데이터 위치 | 비고 |
|------|------|-----------|-------------|------|
| **M0 표준** | Docker + WSL 2 + NVIDIA GPU 정상 | GPU 이미지 컨테이너 | 볼륨 `appdata`, 바인드 `./exports` | 가장 빠름. 이미지 디스크 사용량 큼 |
| **M1 CPU 모드** | Docker 정상, GPU 사용 불가 | CPU 이미지 컨테이너 (`APP_DEVICE=cpu`) | 위와 동일 | 기능 동일, 속도만 느림 |
| **M2 WSL 2 직접 실행** | WSL 2는 되지만 Docker Desktop이 불가(라이선스·정책·용량) | WSL 2 Ubuntu 안에서 가상환경 실행 | WSL 리눅스 홈 아래 `appdata`, `./exports` | GPU가 있으면 사용 가능 |
| **M3 Windows 네이티브** | 관리자 권한 없음·Docker 설치 불가·BIOS 가상화 불가 | Windows에서 가상환경(venv) + 시작 스크립트 | 사용자 지정 로컬 폴더(NTFS)의 `appdata`, `./exports` | GPU가 있으면 Windows용 CUDA 빌드로 사용 가능 |
| **M4 최후 수단** | RAM 부족 등으로 로컬 학습이 어려움 | 학습만 무료 클라우드 노트북에서, 웹앱은 결과 조회 위주 | 결과 파일을 `./exports`로 가져와 조회 | "단독 실행" 목표에서 벗어남. 다른 방법이 모두 막혔을 때만 |

### 8-2. 폴백 시나리오별 세부

**A. GPU 사용 불가 → M1 (CPU 모드)**
- 원인 예: NVIDIA GPU 없음, 드라이버 미지원, 구형 GPU로 PyTorch CUDA 빌드 미지원, 컨테이너에서 GPU 미인식.
- 조치: CPU 이미지 사용, `APP_DEVICE=cpu`. 앱은 시작 시 자동으로 CPU를 선택하므로 사용자가 별도 설정할 필요가 없음.
- 동작 차이: 기능 동일. 학습 시간이 늘어나므로 화면에 예상 시간과 "CPU 모드" 표시, 에포크·모델 크기의 기본 상한을 낮춰 제안.
- 효과: 이미지가 작아 디스크 15GB 조건에도 유리.

**B. Docker 설치 불가 → M2 또는 M3**
- 원인 예: 관리자 권한 없음, 기관 정책, 디스크 부족, Docker Desktop 라이선스 우려.
- 조치: WSL 2가 가능하면 M2(WSL 2 안에서 직접 실행), 그것도 안 되면 M3(Windows 네이티브).
- 데이터: `appdata`는 컨테이너 볼륨 대신 지정 폴더 사용. Windows 네이티브 NTFS 로컬 폴더는 SQLite 잠금 문제가 없으므로 그대로 사용 가능(단, 클라우드 동기화 폴더 — OneDrive 등 — 는 피함).
- 시작·종료: 구현 단계에서 `start`/`stop` 스크립트를 함께 제공. 환경 변수로 경로와 포트를 지정.
- GPU: 네이티브에서도 GPU 사용 가능(Windows용 CUDA PyTorch). 이 경우 Docker 불가와 GPU 불가는 독립적으로 조합됨.

**C. 가상화 불가 → M3**
- 먼저 BIOS 가상화 활성화를 시도(ENV_CHECK 2-3절). 켤 수 없거나 잠겨 있거나 PC가 가상 머신이면 WSL 2·Docker 모두 불가.
- 이 경우 M3 하나뿐이며, 이후 구성은 B의 M3와 동일.

**D. 조합 규칙**

| Docker | GPU | 결과 |
|--------|-----|------|
| 가능 | 가능 | M0 |
| 가능 | 불가 | M1 |
| 불가 | 가능 | M2 또는 M3 (GPU 사용) |
| 불가 | 불가 | M2 또는 M3 (`APP_DEVICE=cpu`) |

### 8-3. 폴백 검증 원칙

- 어느 모드에서든 **같은 자동 스모크 테스트**(작은 샘플 CSV로 업로드 → 학습 → 내보내기 1회)를 통과해야 그 모드를 "지원"으로 표시합니다.
- M0/M1은 컨테이너 안에서, M2/M3는 네이티브에서 각각 한 번씩 실행해 결과 지표가 허용 오차 이내로 재현되는지 확인합니다.

## 9. 리스크와 대응

| 리스크 | 영향 | 대응 |
|--------|------|------|
| 8GB RAM에서 OOM | 학습 중단, 컨테이너 종료(137) | 워커 1개, 데이터·모델 상한, WSL/컨테이너 메모리 한도, 풀 손상 시 자동 복구 |
| 디스크 15GB 부족 | 이미지 빌드·학습 실패 | 기본 CPU 이미지, 미사용 이미지 정리 안내, 디스크 여유 경고 |
| SQLite 손상·잠금 | 이력 유실 | 명명된 볼륨에 저장, WAL, 짧은 트랜잭션, 연결 비공유, 백업 내보내기 |
| 취소가 안 되는 학습 | 자원 점유 | 협조적 취소 + 풀 강제 재생성 |
| 학습이 지나치게 오래 걸림 | 자원 점유, 사용자 대기 | 최대 학습 시간(기본 10분) 도달 시 자동 `timeout` 처리(5-2절) |
| 앱 재시작 시 잡 상태 불일치 | 화면과 실제 상태 불일치 | 시작 시 `running`을 `interrupted`로 복구(5-2절) |
| CP949/BOM 등 인코딩 문제 | 한글 깨짐 | 자동 감지(UTF-8 → CP949 → EUC-KR, 수동 지정은 후속), 내보내기 BOM 옵션 |
| 바인드 마운트 권한·한글 경로 | 내보내기 실패 | ASCII 경로 권장, 구현 시 권한 점검 항목 포함 |
| GPU 드라이버·CUDA 불일치 | GPU 인식 실패 | 자동 CPU 폴백, 화면에 원인 표시 |
| 포트 충돌 | 접속 불가 | 포트를 환경 변수로 변경 가능하게, 시작 스크립트에서 사전 점검 |
| 소규모 데이터에서의 과적합 | 성능 착시 | 검증 분할 기본 적용, 조기 종료, 지표를 학습·검증 나란히 표시 |

## 10. 열린 결정 사항

| 항목 | 기본 제안 | 확정 시점 |
|------|-----------|-----------|
| 웹 프레임워크 | Python + FastAPI(uvicorn) | 구현 시작 전 |
| UI 방식 | 서버가 제공하는 가벼운 정적 페이지 + 폴링 (별도 프론트엔드 빌드 도구 없음) | 구현 시작 전 |
| 딥러닝 프레임워크 | PyTorch (CPU/GPU 빌드 분리) | 구현 시작 전 |
| 진행률 전달 | **확정·구현 완료(STEP 6)**: 워커→디스패처는 멀티프로세싱 Queue, 디스패처→브라우저는 SSE(SQLite를 1초 주기로 폴링해 변경분만 전송) | 완료 |
| 지원할 문제 유형 | 분류·회귀 (다중 라벨·시계열은 제외) | 착수 시 |
| 마이그레이션 도구 | 자체 순차 스크립트 | 구현 시작 전 |
| 폴백 지원 범위 | M0·M1 필수, M2·M3는 스크립트 제공 수준, M4는 문서 안내만 | 착수 시 |

## 11. 착수 순서 (구현은 아직 시작하지 않음)

1. **환경 확정**: ENV_CHECK 4-1의 미확인 항목(RAM, 디스크, GPU)을 채우고 실행 모드(M0/M1)를 결정.
2. **골격 설계**: 저장소 구조와 환경 변수 규약 확정.
3. **컨테이너 골격**: 헬스체크만 응답하는 최소 앱 + 볼륨·바인드 마운트 동작 확인.
4. **저장소 계층**: SQLite 스키마와 잡 상태 머신.
5. **워커**: ProcessPoolExecutor(max_workers=1) 잡 실행, 취소, timeout, 복구.
6. **학습 파이프라인**: 전처리 → MLP 학습 → 평가 → 내보내기.
7. **UI**: 업로드 → 프로파일 → 학습 → 결과.
8. **폴백 검증**: CPU 모드와 네이티브 모드에서 스모크 테스트.
